## 二、P1 已交付项（含验收办法）

### C1 城池距离判定 —— 解决「太远就弹 / 弹错城」
**病灶（已纠偏）**：代码原本就在用世界坐标距离（`CityMarkers` 无 transform，`marker.position` 直接取自 `cities.json` 的 `map_x/map_y`，范围 700~20556，与地形 21256×21826 同坐标系）。真正的问题是 `d < 130.0` **一刀切**：都城图标约 150px 宽（玩家站到城墙根下还弹不出菜单），小村寨不到 70px（隔着一条街就糊上来，且常选中旁边更大的城）。

**改动**：`04-Demo/scripts/world/world_map.gd`
- 判定改为 **到城池「边缘」的距离** = 中心点距离 − 占地半径；半径按 type/level/is_capital 分级（`PLACE_RADIUS` 表，city 62 起步、每级 +6，都城 78 起）
- 显式用 `global_position` 计算（防止将来给 `CityMarkers` 加 transform 时算错）
- 候选排序：屏幕外 +1200 重罚 → 朝着走的方向 −18 加权 → 边缘距离小者优先
- 顺手修：`Hint` 从「所有范围内的地点都显示」改成**只显示最终选中的那一个**（两个城挨着时会冒出两串「▲ 进入」）；全景模式下统一收起 Hint（旧代码残留）

**验收**：进南中，靠近云南/建宁逐个走一遍 —— ① 走到城门口即提示一次；② 两城相邻时菜单只指向玩家实际靠近的那个；③ 屏幕外远处的城不再被选中。

### C4 地图边界硬限制
**病灶（核对数据后发现）**：旧逻辑把玩家 clamp 在「所有古州的**并集矩形**」里，而并集会圈出**不属于任何州的虚空角落**（兖州+豫州并集的东南角）。玩家能走进去，地形上却是空的 —— 观感就是「走出了地图」。

**改动**：
- `scripts/services/region_service.gd`：新增 `walkable_rects()`（本辖区各古州 rect + 与本区域矩形有交集的邻接区域 rect）、`clamp_to_walkable()`
  - 邻接 rect 也要放进集合，否则多州交界处就成了走不过去的空气墙
- `scripts/world/player_controller.gd`：新增 `walk_rects` + `bounds_blocked(dir)` 信号；落到所有矩形外时拉回最近矩形边缘并清掉向外速度分量 + `sync_into_region()`
- `scripts/world/world_map.gd`：注入 `walk_rects`；读档/出城/战斗归来时把坐标夹回地面（`return_pos` 可能是别的区域的旧坐标）；撞墙给出明确提示（前方有邻接州则提示「再往前便是 XX」，否则「前方已是无路之地」），2.5 秒节流

**验收**：沿区域边界四个方向各推到底；任何时候角色不会进入无地形区域；撞墙有提示而不是"静默卡住"。

### C2 在野武将先看后招
**病灶**：酒馆列表点一下就直接 `_do_recruit_hero` 扣钱入队，玩家没法判断这人值不值这笔钱；门槛不满足时整行还被灰掉。

**改动**：`04-Demo/scripts/city/city_scene.gd`
- 列表行改为打开详情面板：名帖（姓名/字/势力/称号）→ 能力（四维 + 评级 + 均值）→ 特技 → 列传 → 招募条件（金/名声/恶名逐项标出当前值是否达标）
- 面板底部三按钮：**交谈**（按难度给一句台词 + 告知眼下卡在哪）、**招募（金额）**（门槛不满足时禁用并标红原因）、**返回名单**
- 招募完成后 `_reopen()` 回酒馆列表，流程不跳断

> 备注：`CityService.give_gift()` 只对**已入队**武将生效（`has_hero` 前置检查），对在野武将没有落点，所以没强塞「赠礼」按钮。若要加，需先给 CityService 增加「在野武将赠礼 → 提升招募意向」的规则与存档字段，工作量会从「小」升到「中」。

### C3 空阵 1v1
**病灶**：布阵界面允许 0 支部队开战，进战场后 `_initial_ally_count = 0`，演的是一场必败的兵力对冲。

**改动**：空阵时跳过部队战，直接打一场主角单挑，胜负即整场遭遇结果。
- `scripts/autoload/game_state.gd`：新增 `duel_only`（瞬时标记，不入存档，`reset` 时复位）
- `scripts/battle/formation_editor.gd`：开战时 `GameState.duel_only = (_count_filled() == 0)`
- `scripts/battle/battle_scene.gd`：
  - 战前决断面板在 duel_only 时变成「孤身赴敌」：隐藏点将/个人技区（对单挑无用），只留「出阵单挑」
  - `_on_duel_finished()` 里 duel_only 分支：构造 zero-summary 直接走既有 `_on_battle_finished()` —— 复用原本的胜利奖励（金币/经验/名声/俘虏）与失败惩罚链路，不另造一套结算
  - 敌阵无将（`enemy_of_encounter` 为空）时自动退回常规流程，不会卡死
  - 演练模式解禁单挑（旧代码 `btn_duel.disabled = ... or GameState.drill_mode` 会挡住空阵演练）

**验收**：布阵页全部清空 → 开战 → 弹出单挑；打赢直接出结算面板（含金币/经验/名声与俘虏判定）；打输走失败结算且不扣兵力（本就无兵）。

### ✅ P3-2 商店库存为 0 —— 已修复

**病灶（查实，非猜测）**：`city_scene.gd` 市场「买进」行的文案写的是 **「库存 %d」**，却取了 `GameState.get_item_count(iid)` —— 那是**玩家自己的持有数**。商店本身无限供货，所以玩家身上没这件东西时，货架上赫然显示「库存 0」，观感就是「这家店被买空了」。

**改动**：买进行文案改为「你持有 N 件」，把「店里的货」和「你身上的货」语义分开。

### ✅ P3-3 打开自己背包出售 —— 已修复

**病灶（查实）**：市场「卖出」区遍历的是 `DataManager.get_market_goods()` 里 `kind == "item"` 的那几件（全市场表只有 7 条，多数是资源类），**玩家背包里的战利品、装备、道具一件都卖不掉** —— 明明身上有货，市场却说没得卖。

**改动**：卖出区改为直接遍历真实背包 `GameState.inventory`：凡在物品表中查得到且有定价（`price > 0`）的都可出售；无定价的任务/剧情道具自动跳过，避免 0 金白给。卖出按钮文案补上持有数。行构件抽成 `_add_market_sell_row()` 单独传参，避免 lambda 捕获循环变量导致所有行卖同一件。

> 备注：`NpcTradePanel`（路上NPC / 行商交易）的出售页**本来就是遍历背包**的，这部分一直是好的，没动。所谓"面板不居中"在该面板里也已由 `CenterContainer` 处理；如有具体场景下的偏移现象，报场景名+分辨率即可定位。

### ✅ P3-1 城池内 NPC 交互 —— 已修复

**病灶（查实）**：`npcs.json` **全表只有 8 个 NPC，且全部挂在 `scene_40`（南中那一座城）**。其余 100+ 座城的城里 `_spawn_city_npcs()` 什么都生不出来 —— 城里空无一人，"城内 NPC 交互"根本没有对象。另一半问题：即便有 NPC，没有专属对话时 `_on_walk_enter()` 只弹一串「……」，点下去像坏了。

**改动**：
1. `npcs` 表对本城无数据时，按本城**实际开放的建筑**用 `CharacterService.BUILDING_NPC_CLASS` → `npc_template_of_class()` 从 heroes6 取模板人物补位（衙署官吏/市井商贾/铁匠铺主/酒家主人/军中教头）
2. 补位 NPC 的 `npc_type` 映射到 `npc_stock.json` 的货单分组（official/merchant/blacksmith），所以**他们能交易**（走原有的 `_walk_trade_btn` 判定，无需改逻辑）
3. 无专属对话时，按身份给一句兜底台词（`NPC_SMALLTALK`），不再干巴巴显示「……」

**验收**：进任意一座城（比如中原/江东的城）→ 广场上应有人且可走近搭话；商铺/铁匠类 NPC 走近会出现「交易」按钮；点了至少有台词反馈。

### 跑商系统（paper prototype → 落地）

**原状（为什么必须做）**：旧模型 `sell_price = buy_price × 0.55`，且买入价只按城池等级缩放 —— **在任何城买入再卖出都亏，跑商在数学上不成立**；`cities.json` 的 `commerce`（10~70）与 `specialty`（粮仓 62 / 军屯 45 / 商埠 3）两个字段**一直零消费**。

**新模型**：`买入价 = 基础价 × 等级系数 × 商业系数 × 特产系数`；`卖出价 = 该城买入价 ×(commodity_sell_ratio + sell_bonus)`。商业越繁荣货源越足、物价越低；粮仓粮贱矿贵，军屯产矿缺粮，商埠百物平价且收货价 +0.08。

**参数不是拍的**：先用 Python 对 110 城 × 3 物资做全配对（11990 城对/物资）仿真网格搜索。踩到一个反直觉点 —— 粮仓城的 commerce 均值只有 13.6（最穷），商业系数天然**对冲**掉它的特产折扣，导致 food 价差被抹平（仅 5.6% 城对可赚）而 wood/iron 过剩（25%）。把 `commerce_weight` 从 0.010 降到 0.004、并给 food 单独放大特产 gap 后才拉平。

**标定结果**（GDScript 探针实测，与 Python 仿真一致）：

| 物资 | 买入价区间 | 盈利城对 | 中位毛利 | 最佳路线 |
|---|---|---|---|---|
| 粮草 | 143~311 | 20.3% | 12% | 庐陵→下邳 净 87/批 |
| 木材 | 123~248 | 24.1% | 22% | 零陵→西河 净 61/批 |
| 铁矿 | 132~265 | 24.1% | 22% | 零陵→西河 净 64/批 |

- **无刷金漏洞**：同城买卖回收率恒为 0.74~0.82（商埠 0.82），原地倒卖必亏（探针全量扫描 `恒亏=true`）。
- **限流**：每城每日进货 8 批（`daily_buy_pack_limit`），跨日重置（探针实测第 9 批被拒、次日恢复满额）。
- **可决策**：市场每行标注「价低 -23% / 价平 / 价高 +42%」（相对天下均价），玩家不必背价格表。
- **经济不失衡**：8 批/日 × 中位路线 ≈ 176~256 金/日，约为一场遭遇奖励（中位 390）的一半，且要付出跑图时间与粮耗。

**改动文件**：`assets/data/shop_goods.json`（新增 `settings.trade`）、`scripts/city/city_service.gd`（`level_factor`/`commerce_factor`/`specialty_factor`/`resource_buy_price`/`resource_sell_price`/`remaining_trade_quota`/`realm_avg_price`/`price_tag` + `buy_resource` 配额校验）、`scripts/autoload/game_state.gd`（`city_trade_today` 及跨日重置/存档）、`scripts/city/city_scene.gd`（市场买进/售出改用跑商价 + 价签 + 额度提示）。

**验证**：compile 66/66（1 条基线假错）、scene 全过、smoke 0 ERROR（1 条基线音频警告）；探针 `scenes/probe/_probe_trade.tscn` 实测后已删。

**纸面原型**（`tools/_prototype_trade_sim.py`，commit `156f92a`）：路线图要求"跑商须 paper prototype 先行"，故另立脚本，分两段 —— 第一段是用 ad-hoc 公式验证"跑商是否值得做"；第二段**逐行对齐 `city_service` 的定价公式、参数直接读 `shop_goods.json`**，回头验证已经写进游戏的那套数字。

| 判据 | 结果 |
|---|---|
| 正期望 | 最优线 庐陵→下邳（粮）+696 金/日，与一场遭遇奖励（中位 390）同量级，不碾压战斗 |
| 有风险 | 35970 条城对×物资中 45.6% 可盈利，中位线路 −96 金 —— 瞎走必亏，选线是真决策 |
| 同源防刷 | 同城原地倒卖"能赚"的组合 **0 条**，回收率恒 0.737~0.823 |

原型本身也修掉三个量纲错误（都是一次性的，已提交留档）：

1. **公式悬崖**：大宗压价 `mid×2/(1+qty/260)` 无下限，本金 3000 以上期望净收益转负（−48%/金）。加"压到基准价 0.9 就不再跌"的下限后曲线被压平。
2. **单向记账**：只记 `a→b` 会把"该走 b→a"的城对全记成大亏，中位收益假负数。改为取两方向最优 —— 玩家当然选有利方向。
3. **重复计价**：`resource_buy_price` 返回的**已经是一整批的价**，价差再乘 `pack` 等于按单价算了两遍，把 696 金放大成 69600 金。

**注**：原型的资本曲线因此是压平的（68.9%→53.5%）而非边际递减，这是 ad-hoc 公式的产物，**不能用来论证边际递减**；真正的限流由游戏内 `daily_buy_pack_limit = 8` 承担，不依赖压价。
